# Penalis Platform — Project Specification

Status: initial implementation, repository-verified only.
Last updated: 2026-10-22.

## 1. Purpose

`penalis-platform` is a self-contained WordPress plugin that adds:

1. A controlled account lifecycle for new Penalis writers.
2. Server-side authorization for writing and publishing.
3. A React writing dashboard mounted on a plugin-managed frontend route.
4. Native WordPress REST integration for articles, media, taxonomy, and account operations.

The existing public site, theme, Elementor content, posts, comments, media, and
legacy contributor accounts remain untouched by activation and normal operation.

## 2. Architecture

| Concern | Decision |
| --- | --- |
| Runtime | WordPress plugin (PHP), no separate server |
| Dashboard | React 18 + TypeScript, built with Vite |
| Delivery | Static assets in `build/`, enqueued only on the dashboard route |
| Auth | Native WordPress cookies and `wp_rest` nonce |
| Authorization | WordPress capabilities + explicit account-status checks |
| Content | WordPress posts, categories, tags, media, metadata |
| Data storage | User meta for account status/tokens; options for plugin settings |
| Admin workflow | WordPress admin list table under **Users → Penalis Writers** |
| Email | `wp_mail()` with failure reporting and retry-safe token behavior |
| Avatars | Storage shared with One User Avatar; this plugin serves avatars when that plugin is inactive |
| Uninstall | Non-destructive by default; explicit opt-in for data removal |

### Why Vite instead of `@wordpress/scripts`

Vite provides a small, fast React/TypeScript setup, emits a deterministic asset
manifest, and has no WordPress runtime dependency. WordPress integration is
implemented explicitly:

- `@vitejs/plugin-react` for JSX.
- `build/manifest.json` is generated by Vite.
- `Penalis_Dashboard` reads the manifest and enqueues the hashed entry assets.
- Vite is configured with a fixed `base` and a stable entry name.

The trade-off is that Gutenberg packages are not automatically bundled by
`@wordpress/scripts`. The dashboard deliberately uses a pragmatic editor:
title, content textarea/HTML, categories, tags, excerpt, featured image, and
media insertion. It does **not** claim to be a block editor replacement. The
content is submitted to the native WordPress posts endpoint and rendered by the
existing theme exactly like any other post.

### Avatar provider

Profile photos are stored as an attachment ID in `{prefix}user_avatar`, the key
One User Avatar uses, so existing assignments survive and both plugins read the
same data.

- While One User Avatar is active it stays the only provider. This plugin writes
  that storage and registers no avatar filter, so the rendered avatar can never
  depend on hook order.
- When One User Avatar is inactive this plugin registers `pre_get_avatar_data`
  and resolves the attachment for both `get_avatar()` and `get_avatar_url()`,
  including the 2x srcset entry. It honours `force_default`, falls back when the
  attachment is missing or is not an image, and leaves rendering to WordPress
  when a user has no photo.
- The site default photo lives in the `avatar_default_wp_user_avatar` option and
  applies only while `avatar_default` is `wp_user_avatar`, mirroring One User
  Avatar. It is managed under **Users → Penalis Writers**.
- Deactivating One User Avatar therefore needs no data migration: the same meta
  is read by this plugin, and reactivating that plugin hands rendering back to it
  while this plugin's filter stays dormant.
- Uninstall leaves `{prefix}user_avatar` in place even when data removal is
  enabled: the key is shared with One User Avatar and may still be owned by that
  plugin.

## 3. Account lifecycle

States are stored in user meta `_penalis_account_status`:

```
pending_verification -> pending_approval -> active
                              |              |
                              v              v
                           rejected       suspended
```

- `pending_verification`: registered, email not yet confirmed.
- `pending_approval`: email confirmed, awaiting administrator decision.
- `active`: approved writer with publishing capability.
- `rejected`: administrator declined the application.
- `suspended`: previously active writer whose access was revoked.

Additional metadata:

| Meta key | Meaning |
| --- | --- |
| `_penalis_access_enabled` | `1` only for accounts explicitly enabled by this plugin |
| `_penalis_email_verified` | `1` after successful verification |
| `_penalis_registered_at` | Registration timestamp |
| `_penalis_approved_at` | Approval timestamp |
| `_penalis_approved_by` | Administrator user ID |
| `_penalis_status_log` | Bounded audit log of status transitions |
| `_penalis_display_name_mode` | Preferred public name source: `auto`, `first`, `last`, `username`, `custom`; absent means `custom` |
| `{prefix}user_avatar` | Profile photo attachment ID, shared with One User Avatar |
| `_penalis_verification_token_hash` | SHA-256 hash of the raw token |
| `_penalis_verification_token_expires` | Expiry timestamp |
| `_penalis_verification_token_created` | Issue timestamp for resend throttling |

Raw verification tokens are never stored. Tokens are 32 random bytes encoded as
URL-safe base64, hashed with SHA-256, and looked up by hash. Because the lookup
uses a full 256-bit hash of high-entropy random data, matching the stored value
does not reveal the raw token.

### Legacy contributor safety

Legacy accounts are **not** assigned `_penalis_access_enabled`. The plugin uses
this explicit eligibility flag, not the WordPress role, to decide whether an
account may authenticate through the dashboard and whether it may publish.

Legacy accounts therefore:

- Keep their existing role, password, posts, and author relationships.
- Are not promoted to `penalis_writer`.
- Cannot log in to the dashboard unless explicitly enabled by an administrator.
- Cannot use password reset to gain dashboard access while disabled.
- Are denied write capabilities while access remains disabled, so an existing
  browser session cannot write.

If an administrator explicitly sets `_penalis_access_enabled = 1` for a legacy
account, that account returns to native WordPress behavior for its existing
role; it is still not given the dashboard workflow.

This is enforced on the `authenticate` filter, the `allow_password_reset`
filter, the `user_has_cap` filter, and REST permission callbacks.

A future "claim legacy profile" flow must implement email/domain ownership proof
and is explicitly out of scope.

## 4. Roles and capabilities

Role `penalis_writer`:

| Capability | Granted |
| --- | --- |
| `read` | yes |
| `upload_files` | yes |
| `edit_posts` | yes |
| `publish_posts` | yes |
| `edit_published_posts` | yes |
| `delete_posts` | yes |
| `delete_published_posts` | yes |
| `edit_others_posts` | no |
| `delete_others_posts` | no |
| `publish_others_posts` | n/a (core has no such cap) |
| `manage_categories` | no |
| `moderate_comments` | no |
| `manage_options` | no |
| `list_users` / `promote_users` | no |
| `install_plugins` / `switch_themes` | no |
| `unfiltered_html` | no |

Server-side guards additionally:

- Force `post_author` to the authenticated user on create.
- Reject author changes on update.
- Reject writes when the account is not `active`.
- Reject writes to posts not owned by the user.
- Strip privileged fields such as `status` values other than the allowed set.
- Prevent role changes to `penalis_writer`/administrator through profile updates.
- Block `penalis_writer` from native REST endpoints that would bypass checks
  (`/wp/v2/users`, `/wp/v2/settings`, `/wp/v2/plugins`, `/wp/v2/themes`, etc.).

## 5. REST design

### Custom namespace: `penalis/v1`

| Route | Method | Auth | Purpose |
| --- | --- | --- | --- |
| `/registration` | POST | public, rate-limited | Create pending account |
| `/verification/resend` | POST | public, rate-limited | Reissue verification email |
| `/verification/confirm` | POST | public, token | Consume verification token |
| `/account` | GET | logged in | Current account state |
| `/account/profile` | POST | logged in | Update safe profile fields |
| `/account/password` | POST | logged in, enabled | Change own password |
| `/account/avatar` | POST | logged in | Assign the profile photo from own media (One User Avatar) |
| `/account/avatar` | DELETE | logged in | Detach the profile photo |
| `/articles` | GET | active writer | Paginated own articles |
| `/articles/(?P<id>\d+)` | GET | owner | Single own article |
| `/articles/(?P<id>\d+)/publish` | POST | owner + active | Publish own draft |
| `/articles/(?P<id>\d+)/unpublish` | POST | owner + active | Return own post to draft |
| `/media` | GET | active writer | Paginated own media |
| `/tags` | POST | active writer | Create or reuse a tag |

Article create/update uses native `/wp/v2/posts` so WordPress handles revisions,
taxonomies, sanitization, and response shaping. A `rest_pre_insert_post` filter
enforces ownership, author, status, and featured-media rules for writers.

### Native endpoint hardening

For users with `penalis_writer`:

- `/wp/v2/users` and `/wp/v2/users/me` are restricted to self-read only.
- `/wp/v2/settings`, `/wp/v2/plugins`, `/wp/v2/themes`, `/wp/v2/block-types`
  writes are denied.
- `/wp/v2/posts` list queries are forced to the current author.
- `/wp/v2/media` list queries are forced to the current author.
- `/wp/v2/comments` moderation endpoints are denied.

Administrators and editors are unaffected.

## 6. Registration and verification

Registration collects:

- `display_name` (2–80 chars)
- `user_login` (3–60 chars, sanitized)
- `user_email` (valid, normalized)
- `password` (minimum 12 chars; server-side check)
- `penalis_consent` (explicit acceptance)

Server-side controls:

- Nonce verification for browser-originated requests is **not** used for
  anonymous registration (WordPress nonces require a session); instead the
  endpoint uses strict validation, honeypot field, per-IP rate limiting, and
  duplicate-safe responses.
- Duplicate email/login responses are intentionally generic to limit
  enumeration. The response never states whether an address exists.
- Passwords are hashed by `wp_insert_user()`.
- New users get the `penalis_writer` role but `_penalis_access_enabled = 0`
  and status `pending_verification`; they cannot publish until approved.
- Verification token: 32 random bytes, 24-hour expiry, single use.
- Resend is throttled to once per 10 minutes per account and rate-limited per IP.
- If `wp_mail()` fails, the account remains `pending_verification`, the failure
  is recorded in bounded user meta, and the API returns a generic delivery
  warning. State does not advance silently.

Email delivery is assumed to depend on the host's mail configuration. The
plugin does not assume reliable delivery and documents manual verification.

## 7. Approval and suspension

Administrators use **Users → Penalis Writers**:

- Filter by status.
- Approve, reject, suspend, or reactivate with nonce-protected actions.
- View bounded status history.
- Resend verification for unverified accounts.
- Choose the default profile photo used for accounts without one.

The default photo is stored in the `avatar_default_wp_user_avatar` option and
only applies while `avatar_default` is `wp_user_avatar`, matching One User
Avatar's behaviour.

Transitions are centralized in `Penalis_Account_Status::transition()` and
validate allowed source/target pairs. Every transition appends to a bounded
audit log (last 20 entries).

Suspension removes publishing ability immediately:

- `_penalis_account_status = suspended`
- `_penalis_access_enabled = 0`
- Role remains `penalis_writer` for historical attribution, but all server-side
  checks deny writes and native REST requests.
- Existing posts are not deleted or reassigned.

## 8. Dashboard

Route: a plugin-managed page with shortcode `[penalis_dashboard]` and the
`/penalis-dashboard/` slug. The page is created once on activation if missing.

Views:

- **Overview** — account status, article counts, recent articles.
- **My Articles** — paginated list with status filters and actions.
- **Editor** — create/edit title, content, excerpt, categories, tags, featured
  image, inline media insertion.
- **Profile** — first name, last name, public name choice (first + last, first,
  last, username, or a custom pen name), bio, website.
- **Settings** — account status, password change, sign out.

UX requirements implemented:

- Loading, empty, error, and validation states.
- Status banners for pending/rejected/suspended accounts.
- Disabled write actions when the account is not active.
- Responsive layout with a mobile navigation pattern.
- No auth tokens in `localStorage`; nonce passed via `wp_localize_script`.

## 9. Performance and caching

- Dashboard assets enqueued only on the dashboard page.
- Article/media lists paginated (default 10, max 50).
- REST responses use `context=edit` only for the owner.
- Admin list tables use `WP_User_Query` with pagination.
- No unbounded queries.
- Authenticated dashboard page sends `nocache_headers()` and a
  `Cache-Control: private, no-store` header.
- Custom REST responses set `Cache-Control: no-store` for private data.
- Activation/deactivation perform no destructive migrations.
- Status log capped at 20 entries; email failure metadata is bounded.

## 10. Assumptions requiring local verification

These are **not** verified against the live site:

1. The existing theme renders standard post content, title, excerpt, featured
   image, categories, and tags without requiring custom fields.
2. Elementor does not override single-post rendering for writer articles.
3. The site's mail configuration can deliver `wp_mail()` messages; SMTP may be
   required.
4. The dashboard page slug `/penalis-dashboard/` does not conflict with an
   existing page. If it does, the plugin reuses/creates a suffixed slug and
   stores the ID in an option.
5. Existing contributor accounts have no `_penalis_access_enabled` meta.
6. The site uses standard WordPress authentication without a custom SSO plugin
   that bypasses `authenticate`.
7. Permalinks are enabled (pretty permalinks) for clean REST and dashboard URLs.
8. No page cache serves authenticated dashboard HTML publicly; the plugin sends
   no-store headers but host/CDN configuration must also exclude logged-in users.

## 12. Known limitations

- The editor is not a full Gutenberg block editor; it submits HTML/text content.
- Email templates are plain text; no HTML templating system.
- No CAPTCHA integration; honeypot + rate limiting are used.
- Rate limiting uses transients and is per-IP/per-account, not distributed.
- Legacy profile claiming is out of scope.
- Multisite behavior is not specifically implemented or tested.
- No custom database tables are introduced.
- Profile photos share One User Avatar's storage. While that plugin is active it
  remains the provider; once it is inactive this plugin serves avatars from the
  same meta. No crop UI is provided; the image is used as uploaded.

## 13. Manual test checklist

Run these in your local WordPress installation after activating the plugin and
building the frontend. Each test states setup, action, and expected result.

### Setup

1. Build and deploy: `npm ci && npm run build`, then ensure `build/` is present
   in the installed plugin directory.
2. Activate the plugin.
3. Save **Settings → Permalinks** once.
4. Confirm the **Writing Dashboard** page exists and the slug is reachable.
5. Configure outgoing email (SMTP recommended) and confirm you can receive mail.
6. Have an administrator account and at least one existing contributor account
   available.

---

### 1. A visitor can register

**Setup:** Sign out or use a private window.
**Action:** Open the dashboard page, choose **Create a writer account**, complete
the form, accept the terms, submit.
**Expected:** A success message appears and does not confirm whether the email
already existed. A verification email arrives. No publishing ability is granted.

---

### 2. An unverified account cannot publish

**Setup:** Register but do not click the verification link. Sign in.
**Action:** Open the dashboard. Try to open the editor or call
`POST /wp-json/wp/v2/posts` directly with the REST nonce.
**Expected:** The dashboard shows the verification-pending banner. Article and
media navigation is disabled. The direct API request returns `403` with
`penalis_account_inactive` (or `penalis_forbidden`). No post is created.

---

### 3. A verified account awaiting approval cannot publish

**Setup:** Click the verification link and press **Confirm email address**. Sign
in.
**Action:** Attempt to create an article through the UI and directly through
`POST /wp-json/wp/v2/posts`.
**Expected:** Status shows **Awaiting administrator approval**. Publishing is
disabled. The direct API request is rejected with `403`. No post is created.

---

### 4. An approved writer can create and publish their own article

**Setup:** As an administrator, open **Users → Penalis Writers**, approve the
account.
**Action:** Sign in as the writer, create an article with a title, content,
category, tag, and featured image. Save as draft, then publish.
**Expected:** The draft appears in **My Articles**. Publishing succeeds. The
article appears on the public site with the writer as author. The featured image
renders if the theme supports it.

---

### 5. A writer cannot edit or delete another writer's article

**Setup:** Two approved writers (A and B). Writer B has at least one article.
**Action:** As writer A, request
`GET /wp-json/penalis/v1/articles/<B post id>`,
`POST /wp-json/wp/v2/posts/<B post id>` with modified content, and
`DELETE /wp-json/wp/v2/posts/<B post id>?force=true`.
**Expected:** All return `404` or `403`. Writer B's article is unchanged and not
deleted. Writer A's UI never lists B's article.

---

### 6. A writer cannot assign an arbitrary author to an article

**Setup:** Two approved writers.
**Action:** As writer A, send
`POST /wp-json/wp/v2/posts` with `"author": <B id>` and valid content.
**Expected:** Request is rejected with `403` (`penalis_invalid_author`), or the
author is forced to writer A. It must never create a post attributed to B.
Also try updating an existing own post with another author ID.

---

### 7. A suspended writer cannot continue publishing through direct API requests

**Setup:** An active writer who is currently signed in.
**Action:** As administrator, suspend the writer. Then, using the writer's
existing browser session, call `POST /wp-json/wp/v2/posts` and
`POST /wp-json/penalis/v1/articles/<id>/publish`.
**Expected:** The session is invalidated (user is signed out on next request).
If a session is re-established, requests return `403`. No post is created or
published. The writer's existing articles remain published and attributed.

---

### 8. A writer cannot elevate their own role or capabilities

**Setup:** An approved writer signed in.
**Action:** Attempt `POST /wp-json/wp/v2/users/<own id>` with
`"roles": ["administrator"]`, and attempt `POST /wp-json/wp/v2/settings`.
**Expected:** `/wp/v2/users` and `/wp/v2/settings` are blocked for writers.
The role remains `penalis_writer`. No settings change occurs. Also attempt to
change the email address through the profile API; it should not change.

---

### 9. Unsafe file uploads are rejected

**Setup:** An approved writer signed in.
**Action:** Upload (a) a `.php` file renamed to `.jpg`, (b) an SVG containing
script, (c) a valid PNG.
**Expected:** (a) and (b) are rejected with an upload error. (c) succeeds. The
uploaded file is not executable and appears in the writer's media list.

---

### 10. Private and draft content is not exposed to unauthorized users

**Setup:** Writer B has a draft article.
**Action:** As writer A, query `GET /wp-json/wp/v2/posts?status=draft`,
`GET /wp-json/wp/v2/posts?author=<B id>`, and
`GET /wp-json/penalis/v1/articles?status=draft`.
**Expected:** Results are limited to writer A's own posts, or empty. Writer B's
draft title/content is never returned. Anonymous requests cannot read drafts.

---

### 11. Existing contributor profiles and article-author relationships remain intact

**Setup:** Note an existing contributor's user ID, role, email, and authored post
IDs before activating the plugin.
**Action:** Activate the plugin and browse the public site and author archives.
**Expected:** The contributor still has the same role, email, and posts. Author
archives and URLs resolve. No password or role changed. The contributor cannot
sign in unless an administrator explicitly enabled access.

---

### 12. Existing administrators, editors, and authors retain their workflows

**Setup:** Existing administrator, editor, and author accounts.
**Action:** Sign in to wp-admin with each and perform normal actions: edit posts,
publish, moderate comments, manage users.
**Expected:** Behavior is unchanged. The plugin does not block their REST
endpoints or capabilities.

---

### 13. Plugin activation does not destructively alter existing data

**Setup:** Take a database backup and record post, user, comment, and term counts.
**Action:** Activate the plugin, then deactivate and reactivate it.
**Expected:** Counts are unchanged. No posts, users, comments, terms, or media
are deleted or reassigned. Only the writer role, plugin options, and the
dashboard page are added. Deactivation preserves everything.

---

### 14. Invalid, expired, and reused verification tokens are rejected

**Setup:** An account awaiting verification.
**Action:**
1. Open the verification link, confirm, then reload and confirm again.
2. Modify one character in the token and confirm.
3. Wait past expiry (or set `_penalis_verification_token_expires` to a past
   timestamp via a test tool) and confirm.

**Expected:** Reuse, tampering, and expiry each return a safe error message and
do not change account state. Requesting a new email issues a fresh token; the
old token no longer works.

---

### 15. Registration and API error responses do not reveal private information

**Setup:** An existing account.
**Action:** Register with the existing email, then with the existing username.
Also request a resend for a non-existent address.
**Expected:** Responses are generic and identical in shape for existing and
non-existing accounts. No message confirms that an account exists. No email
addresses, tokens, roles, or internal IDs appear in error output.

---

### Additional checks worth performing

- **Cache headers:** Inspect the dashboard response and
  `/wp-json/penalis/v1/account` for `Cache-Control: private, no-store` and
  `X-Robots-Tag: noindex`.
- **Email failure:** Disable mail, register an account, and confirm the API
  reports a delivery problem and the account stays `pending_verification`.
- **Approval email:** Approve a writer and confirm they receive the activation
  email.
- **Resend throttle:** Request two verification emails within 10 minutes and
  confirm the second is throttled.
- **Theme rendering:** Publish an article and confirm the existing theme renders
  title, content, excerpt, featured image, categories, and tags without custom
  fields.
- **Mobile layout:** Check the dashboard at 375px and 768px widths.
